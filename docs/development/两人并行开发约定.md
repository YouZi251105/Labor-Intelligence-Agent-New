# 两人并行开发约定

版本：1.0  
更新日期：2026-11-01

## 1. 目标

两位开发者通过独立分支并行开发，避免互相等待和频繁冲突，并保证每个阶段都能合并后运行和验收。

基本模式：

```text
main
→ 开发 A 功能分支
→ 开发 B 功能分支
→ 接口先行与 Mock
→ 各自测试
→ PR 互审
→ 合并 main
→ 阶段验收
→ 下一阶段
```

## 2. 角色

### 开发 A

后端、AI、数据和安全。

### 开发 B

前端、证据体验、产品交互和测试。

### 法律内容负责人

由两位开发之外的人员担任。法律条文、案例、规则、期限和文书模板不由开发自行确认。

## 3. 模块责任

| 模块 | 开发 A | 开发 B | 法律内容负责人 |
|---|---|---|---|
| 用户与权限 | 主责实现 | 登录页、路由守卫 | 不涉及 |
| 案件模型 | 主责 | 字段需求和页面 | 确认关系类型和分类 |
| 工作流 | 状态机与接口 | 流程轴和决策树 | 确认阶段和期限 |
| AI 咨询 | 模型、提示词、上下文 | 对话界面和流式展示 | 确认法律表达 |
| 证据上传 | 文件、权限、存储 | 上传和错误状态 | 不涉及 |
| 证据规则 | 按规则实现 | 主责规则产品化与验收 | 主责法律依据 |
| 合同审查 | 提取和结构化结果 | 风险报告页面 | 确认审查标准 |
| 文书生成 | 模板、数据填充、导出 | 编辑、预览和下载 | 主责模板内容 |
| 律师端 | 分配和权限接口 | 页面和工作记录 | 确认服务流程 |
| 管理端 | 数据和权限接口 | 管理页面 | 确认规则配置 |
| 测试 | 后端和安全测试 | 前端和端到端测试 | 法律样例审核 |
| 部署 | 基础设施 | 构建和页面验收 | 不涉及 |
| 文档 | API、开发和安全 | 用户、律师和演示 | 法律说明审核 |

## 4. 文件边界

### 开发 A 可直接负责

```text
backend/app/core/
backend/app/db/
backend/app/models/
backend/app/routes/auth.py
backend/app/routes/cases.py
backend/app/routes/admin.py
backend/app/routes/lawyer.py
backend/app/services/ai.py
backend/app/services/documents.py
backend/alembic/
```

### 开发 B 可直接负责

```text
frontend/src/
docs/user/
docs/lawyer/
docs/demo/
```

### 证据模块

默认拆分：

- A 负责 `routes/evidence.py`、`services/evidence.py`、证据模型、文件权限和接口。
- B 负责证据验证规则、页面、缺口提示、错误文案和验收。

如果 B 要直接修改证据后端，必须先由双方确认，并单独创建分支。

### 共享文件

```text
backend/app/api/v1/router.py
backend/app/models/__init__.py
backend/app/schemas/__init__.py
frontend/src/router/index.ts
frontend/src/types/api.ts
frontend/src/styles/base.css
README.md
```

规则：

- 后端共享文件由 A 负责最终合并。
- 前端共享文件由 B 负责最终合并。
- API 类型以 OpenAPI 和接口契约为准。
- 双方不得在同一时间段修改 `base.css`。

## 5. 接口先行

每个功能开始前，先完成接口约定：

1. A 在 `docs/api/接口契约_v1.md` 写明请求、响应和错误。
2. A 更新 Pydantic Schema。
3. A 运行 OpenAPI 导出。
4. B 根据 OpenAPI 和示例 JSON 开发 Mock。
5. 双方确认状态、枚举和空值规则。
6. 再分别实现。

接口契约变更流程：

```text
修改契约文档
→ 双方确认
→ 后端更新 Schema
→ 导出 OpenAPI
→ 前端更新类型
→ 双方补测试
```

禁止口头修改字段后只改一端。

## 6. Mock 约定

后端尚未完成时，B 使用契约中的固定响应：

- 字段名必须一致。
- 枚举值必须一致。
- 空值必须是 `null`，不随意使用空字符串代替。
- 日期使用 ISO 8601。
- 金额使用整数分或明确标注为字符串，不得混用。
- 错误结构统一为 `{"detail": "..."}`。

Mock 数据不得包含真实身份信息和真实案件材料。

## 7. 分支规则

```text
feat/backend-<feature>
feat/frontend-<feature>
fix/backend-<bug>
fix/frontend-<bug>
docs/<topic>
chore/<topic>
```

要求：

- 一个分支只完成一个可验收功能。
- 分支开发周期建议 1 至 3 天。
- 每天从 `origin/main` 同步。
- 个人功能分支可使用 rebase。
- 已经共享的分支不得强推。
- 合并使用 Squash Merge。

## 8. PR 要求

每个 PR 必须包含：

1. 任务目标和范围。
2. 修改文件列表。
3. 接口变更说明。
4. 测试命令和结果。
5. 截图或录屏，涉及页面时提供。
6. 未完成事项。
7. 是否影响法律内容或对外口径。

Review 重点：

- 是否越权访问案件。
- 是否泄露用户材料。
- 是否把 AI 输出直接当成事实。
- 是否破坏接口兼容性。
- 是否修改了对方负责的文件。

## 9. 测试责任

### A 必须提供

- Pydantic Schema 校验测试。
- 权限与越权测试。
- 文件处理测试。
- AI 结构化输出与回退测试。
- 数据库迁移测试。

### B 必须提供

- 页面状态测试。
- 空数据、加载和错误状态。
- 移动端和键盘操作。
- 关键流程 Playwright 测试。
- 前端类型检查和生产构建。

### 共同验收

- 登录。
- 创建案件。
- 多轮咨询。
- 上传证据。
- 合同审查。
- 生成文书。
- 管理员分配。
- 律师查看。

## 10. 阶段开发规则

阶段目标由 `docs/development/分阶段分工与验收.md` 管理。

只有当前阶段验收通过并合并 `main` 后，才开始下一阶段的主要功能。可以提前做技术调研，不得提前大规模改动共享代码。

## 11. 法律内容协作

工程可以先使用：

- 已有的法律内容数据作为演示草稿。
- 明确的本地演示规则。
- 带“待法律复核”标记的数据。

但正式发布前必须具备：

- 来源 URL 或官方出处。
- 生效日期。
- 复核状态。
- 复核人。
- 版本。

具体规则见 `docs/development/法律内容迁移与责任边界.md`。

## 12. AI 工具协作

AI 工具必须把根目录 `AGENTS.md` 作为入口，并读取：

```text
AGENTS.md
docs/api/接口契约_v1.md
docs/api/openapi.v1.json
docs/development/分阶段分工与验收.md
```

工具只能修改当前任务所属范围，跨范围修改先更新约定。
