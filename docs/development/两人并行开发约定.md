# 两人并行开发约定

版本：2.0
更新日期：2026-11-01

## 1. 目标

两位开发者并行推进，但每个阶段仍然只有一套可运行、可验收的主线。

执行原则：

- 接口先行，双方按同一份契约开发。
- 任务按可独立验收的工作项拆分，不按整个模块粗分。
- 单个工作项建议控制在 0.5 至 1.5 人日。
- 一方完成工作项后直接进入下一项，不等待另一方整条链路完成。
- `main` 始终可运行，阶段功能先进入集成分支。
- 不修改对方负责的业务文件。需要跨边界时，先调整契约和任务边界。

## 2. 角色

### 开发 A

后端、AI、数据、安全和发布基础设施。

### 开发 B

前端、产品交互、证据规则、证据体验和端到端测试。

### 内容复核人员

由两位开发之外的人员担任，负责法条、案例、证据要求、期限、文书模板和对外法律表述。

## 3. 工作负载规则

- 每个阶段开始前，先确认双方任务预算，不把后端全部交给 A、页面和测试全部交给 B。
- 每人每阶段的目标工作量控制在 6 至 8 人日，比较结果以任务编号和验收结果为准。
- 阶段集成负责人额外投入最多 0.5 人日，承担合并、回归和验收记录。
- 一方提前完成时，从本阶段未分配任务中领取独立工作项，不进入对方目录临时改代码。
- 如果某工作项超过 1.5 人日，必须继续拆分后再开始。
- 预计阻塞超过 2 小时，立即切换到不依赖该阻塞的工作项。

阶段集成负责人安排：

| 阶段 | 集成负责人 | 后端门禁 | 前端门禁 |
|---|---|---|---|
| 阶段 2 | 开发 B | 开发 A | 开发 B |
| 阶段 3 | 开发 A | 开发 A | 开发 B |
| 阶段 4 | 开发 B | 开发 A | 开发 B |

集成负责人负责协调合并、补集成测试和记录验收结果，不代表可以绕过另一人的代码审查。

## 4. 模块责任

| 模块 | 开发 A | 开发 B | 内容复核人员 |
|---|---|---|---|
| 用户与权限 | 认证、角色、对象级权限 | 登录、补充资料、路由守卫 | 不涉及 |
| 案件模型 | 数据模型、接口和状态机 | 页面字段、流程轴和决策树 | 确认案件分类和期限 |
| AI 咨询 | 上下文、提示词、模型调用、结构化输出 | 对话界面、历史折叠和错误状态 | 确认法律表达边界 |
| 证据上传 | 存储、文件校验、权限和审计 | 上传交互、进度和错误状态 | 不涉及 |
| 证据规则 | 提供稳定接口和输入输出结构 | 规则模块、规则样例、缺口判断和测试 | 提供并复核法律依据 |
| 合同审查 | 文本提取、结构化审查结果 | 风险报告和人工复核入口 | 确认审查标准 |
| 文书生成 | 模板装配、DOCX/PDF 导出和版本数据 | 编辑、预览、版本切换和下载 | 提供并复核模板内容 |
| 律师端 | 审核、分配、授权和服务记录接口 | 律师工作台和业务页面 | 确认服务流程 |
| 管理端 | 用户、律师、规则和审计接口 | 管理页面和操作反馈 | 确认规则配置口径 |
| 测试 | 后端、权限、文件和接口契约测试 | 前端、E2E、移动端和可访问性测试 | 审核法律样例 |
| 部署 | 数据库、存储、任务队列和生产安全 | 前端构建、页面验收和发布检查 | 不涉及 |


## 7. 契约门槛

每个阶段先完成一个契约工作项，再开始功能开发。

契约工作项必须包含：

1. 请求和响应字段。
2. 枚举、空值和错误结构。
3. 至少一组请求和响应示例。
4. Pydantic Schema。
5. 更新后的 OpenAPI。
6. 前端需要的加载、空数据、失败和部分成功状态。

执行方式：

```text
A 提交契约草稿
→ B 复核页面所需状态
→ 双方确认
→ 契约分支合并 main
→ A、B 分别从最新 main 建功能分支
```

契约阶段最多持续 0.5 人日。B 在此期间可以同步准备页面骨架、状态组件和测试样例，不等待后端完整实现。

契约冻结后需要改字段时：

```text
提交契约变更说明
→ 双方确认兼容影响
→ 更新 Schema 和 OpenAPI
→ 前端更新类型
→ 双方补测试
```

## 8. 分支和合并

命名规则：

```text
docs/stage<N>-contract
feat/backend-<feature>
feat/frontend-<feature>
feat/evidence-rules-<feature>
fix/backend-<bug>
fix/frontend-<bug>
integration/stage<N>
```

合并流程：

```text
main
→ 契约分支 PR
→ 合并 main
→ A、B 功能分支并行
→ 各自 PR 到 integration/stage<N>
→ 集成负责人运行回归
→ integration/stage<N> PR 到 main
→ 双方复核后合并
→ 打阶段验收标记
```

规则：

- 禁止直接向 `main` 强推。
- 一个功能分支只完成一个任务编号。
- 功能分支合并到集成分支时使用 Squash Merge。
- 集成分支合并到 `main` 时使用 PR 和 Merge Commit，保留阶段记录。
- 集成负责人不得跳过对方审查后自行合并自己负责的核心功能。
- 已共享分支不改写历史，不使用强推。

## 9. 统一合并顺序

阶段 2 固定顺序：

1. 契约分支合并 `main`。
2. A 的后端提取、审查和导出接口进入集成分支。
3. B 的证据规则模块进入集成分支。
4. B 的前端页面进入集成分支。
5. B 执行集成回归，A 复核后端和安全结果。
6. 集成分支统一合并 `main`。

后续阶段采用同样顺序。若后端接口尚未实现，前端只能使用契约夹具，不得自行定义另一套字段。

## 10. 测试责任

### 开发 A 必须提供

- Pydantic Schema 和 OpenAPI 一致性。
- 权限与越权测试。
- 文件上传、提取、导出和失败回退测试。
- AI 结构化输出和回退测试。
- 数据库迁移测试。

### 开发 B 必须提供

- 证据规则单元测试和规则夹具。
- 页面加载、空数据、部分成功和错误状态。
- 移动端和键盘操作检查。
- Vitest、类型检查和生产构建。
- 关键流程 Playwright 测试。

### 合并前共同执行

- 后端测试。
- 前端测试、类型检查和构建。
- 关键 Playwright 流程。
- 角色权限冒烟测试。
- 接口契约和实现检查。
- 文档状态和进度说明检查。

## 11. 阶段收口

阶段完成必须同时满足：

- 所有任务编号有完成记录。
- 接口契约、OpenAPI 和前端类型一致。
- 集成分支回归通过。
- 对方完成代码审查。
- 进度文档已更新。
- 法律内容仍标注复核状态。
- 未完成事项进入下一阶段，不藏在代码注释里。

阶段验收后在 `main` 打标记：

```text
stage-2-accepted
stage-3-accepted
stage-4-accepted
```

## 12. 文档权威顺序

发生冲突时按以下顺序处理：

1. `AGENTS.md` 中的强制规则。
2. `docs/api/接口契约_v1.md` 和 OpenAPI。
3. `docs/development/分阶段分工与验收.md` 中的阶段范围、任务负责人和验收条件。
4. 本文档中的协作和合并流程。
5. 根目录进度说明和对外手册。
